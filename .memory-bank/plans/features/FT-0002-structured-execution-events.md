## Feature FT-0002 — Структурированные события выполнения
Epic: `EP-001`. Status: `Done`.
Triage: `ready-for-agent`.

### User value
Результат выполнения задания становится машиночитаемым: что изменено, что без изменений, что пропущено, где ошибки. Для пользователя web ничего не меняется — лог выглядит как раньше. Это основа `--json` в CLI (FT-0004) и проверок в тестах.

### Deliverables
- Модель события: `status` (`changed` | `unchanged` | `skipped` | `warning` | `error`), `scope`, `message`, `details`; плюс служебные события начала/окончания задания и разделители, нужные для текстового лога.
- Все исполнители из `src/tasks` и `CompositeTableTaskExecutor` сообщают события вместо `tableTaskLogger.log(string)`.
- Сборщик событий, из которого можно получить список событий и сводку (счётчики по статусам, `ok`).
- Текстовый рендер событий: web показывает тот же текст (эмодзи, пустые строки, заголовки проектов), что и сейчас.
- «Unknown task» и «API is not available» из `CompositeTableTaskExecutor` становятся событиями `error`, а не `console.error`.

### Context (SSoT links)
- [CLI spec](../../spec/cli/cli.md): черновик схемы результата и соответствие статусов эмодзи. Читать, чтобы модель события совпала со схемой `--json`.
- [Task catalog](../../spec/domain/tasks/index.md): задания и их текущий лог. Читать, чтобы не потерять сообщения при переходе.
- [Architecture guardrails](../../spec/engineering/architecture-guardrails.md): исполнители не знают о React. Читать, чтобы рендер для web жил в delivery.

### Implementation plan
- Expand–contract в пределах одной фичи: сначала интерфейс событий рядом с `TableTaskLogger` (адаптер «события → текст» реализует старый вывод), затем перевод исполнителей по одному, затем удаление `log(string)`.
- Статус выводится из смысла сообщения, а не из эмодзи: 🟢 → `changed`, 🟡 → `unchanged`/`skipped`, ❌/🔴 → `error`. Спорные случаи зафиксировать в спеке задания.
- `scope` — сущность, к которой относится событие (проект/команда, студент, техкарта, дисциплина).
- Web (`App.tsx`) подписывается на текстовый рендер; логика рендера — не в компоненте.
- Actions (`src/actions`), используемые в заданиях, переводятся только там, где они пишут в лог задания; `putMarks*` — в FT-0005.

### Scenarios (acceptance)
#### Setup
- Тестовый лист задания каждого типа (или сохранённый текст лога до изменений).
- Actors: пользователь web.

#### Action
- Запустить задание в try в web до и после изменения.

#### Assert
- Текст лога совпадает построчно (допускаются только исправления опечаток, перечисленные в коммите).
- Сборщик событий для того же прогона даёт непустой список событий с корректными `status` и сводкой; при неизвестном типе задания — одно событие `error`, `ok = false`.

### Tests
- Unit (после FT-0006): текстовый рендер набора событий; сводка по статусам.
